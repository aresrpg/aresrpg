# AresRPG agent custody and Recall

Complete https://aresrpg.world/agents/client.txt first. Pairing alone authorizes no transfers or gameplay.

## Connect and act

The hosted backend actor owns the managed signer and its single game connection. External assistants receive scoped MCP access, never a transaction signer or private key. `tools/list` is the implemented catalog; the SDK custody capabilities below are not a promise that each is exposed as an MCP tool.

For private service integration, `create_agent_connection` from `@aresrpg/sdk/agent-connection` handles challenge authentication, roster updates and read-only fight resync using the actor’s managed personal-message signer. The ordinary SDK uses that actor’s transaction signer and awaited encrypted exact-envelope `transaction_journal`. See [the SDK integration reference](https://aresrpg.world/agents/sdk.txt) and [operator README](https://raw.githubusercontent.com/aresrpg/aresrpg/edge/packages/bot/README.md). The SDK owns resolution, signing, submission and digest recovery; do not construct an unjournaled hosted writer or retry an uncertain digest.

For custody, `agent_character_transfer(sdk)` from `@aresrpg/sdk/agent-transactions` exposes
`offer`, `claim` and `cancel` transaction builders. They reuse personal kiosks and marketplace
policy settlement. `agent_transfer_actions` adds simulation, one-use confirmation and receipts.
Claim the human's exclusive PurchaseCap into the multisig's personal kiosk; selected character IDs,
cap IDs and gas must come from actual state, never examples. Zero price does not waive gas or royalties.

## Human Recall

The browser retains public recovery identities per Google owner. Select the agent character’s
circuit-and-robot tab and use Recall from its context menu. The hosted assistant need not be online.
Restored identities allow recovery, not new handover.

**Recall** uses the human's Google member to authorize a return from the multisig kiosk. It unequips
into that kiosk, then issues exclusive PurchaseCaps for the character and precisely its CURRENT
equipped items. The claim settles their policies and re-equips those items atomically in the human
kiosk. The original delegation loadout is not used; unrelated inventory stays put.
The SDK verifies the offer transaction’s ItemUnequipped events and unchanged newly created
capabilities before review and again before signing. Missing or ambiguous history, ownership or
gear blocks the claim. A failed claim leaves all transfers unexecuted; reconcile uncertain digests
before trying again. Cancelling releases the character and item listings in the source kiosk,
leaving the gear unequipped there. This uses existing contracts and needs no new Move module.
Recall offers and claims through the existing SDK sequence. Both signatures come from the human;
the agent is not asked. The offer needs multisig gas; the claim needs human-wallet gas. A verified
pending return resumes at the claim without another offer. Inventory has no manual character
claim or cancellation controls; the underlying SDK custody builders remain available.

This follows existing custody rules: a fighting character must first return to kiosk custody;
a capability already transferred to a third party is controlled by that holder. Recall does not
revoke the agent's 1-of-2 authority over assets remaining in the multisig.

## Inventory and full return

Both bags use the indexed account inventory. Drag exact items or whole displayed stacks between
them to run the existing offer-and-claim sequence. Coin balances open Deposit or Withdraw with
an explicit amount, Max and the retained reserve. Missing KARES configuration disables that currency.
Incoming item recovery validates each capability’s unchanged creation receipt and excludes gear
belonging to a pending character return. Discovery fetches a shared receipt once per digest within
that invocation; each capability still proves its own version, digest and recipient.

The connected modal’s Disconnect action requires explicit confirmation. It stops hosted work,
drains unresolved transactions, resolves supported fight/dungeon custody and returns assets through
the existing SDK before sweeping balances. Partial or uncertain returns stay stopped for explicit
resume. The SDK’s complete auxiliary audit covers personal kiosks, address-owned assets, proceeds
and staking; this is not another inventory screen. Unknown or unsupported custody fails closed.
Fee quotes precede signing. Never retry an uncertain or executed digest.

## Verification boundary

Gas failures open the existing funding flow for the actual payer: multisig for the Recall offer,
human for the claim. No funds are sent automatically.

Local tests cover identity binding, signed-mode tampering, both custody builders, equipment reads,
Google-member envelope wiring with an explicit verification stub, public identity recovery and
failed/uncertain submissions. Actual Google proof verification, host-key persistence and the full
live handover/Recall round trip remain for the human's manual test after deployment. The optional
`agent_kit.ts` observer is a diagnostic example, not a required runtime or autonomous player.
