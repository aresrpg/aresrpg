# AresRPG agent custody and Recall

Complete https://aresrpg.world/agents/client.txt first. Pairing alone authorizes no transfers or gameplay.

## Connect and act

`create_agent_connection` from `@aresrpg/sdk/agent-connection` handles challenge authentication,
roster updates and read-only fight resync using a supplied transport and personal-message signer.
The Bun transport example is `packages/sdk/examples/agent_transport.ts`. It does not auto-play.

Construct the ordinary SDK with the returned transaction signer:

```ts
import { SDK, sui_transport } from '@aresrpg/sdk'
import { SuiGrpcClient } from '@mysten/sui/grpc'

const client = new SuiGrpcClient({ network: 'mainnet', baseUrl: 'https://fullnode.mainnet.sui.io:443' })
const sdk = SDK({ client: sui_transport(client), network: 'mainnet',
  address: signer.address, sign_transaction: signer.sign_transaction })
```

Use existing character, fight, dungeon and marketplace actions; `packages/sdk/examples/agent_actions.ts`
shows their composition. The SDK owns resolution, signing, submission and digest recovery.
Never retry an uncertain transaction: reconcile its digest first.

For custody, `agent_character_transfer(sdk)` from `@aresrpg/sdk/agent-transactions` exposes
`offer`, `claim` and `cancel` transaction builders. They reuse personal kiosks and marketplace
policy settlement. `agent_transfer_actions` adds simulation, one-use confirmation and receipts.
Claim the human's exclusive PurchaseCap into the multisig's personal kiosk; selected character IDs,
cap IDs and gas must come from actual state, never examples. Zero price does not waive gas or royalties.

## Human Recall

The browser retains public recovery identities per Google owner. Reopen setup and use the saved
identity even if the assistant is offline. Restored identities allow recovery, not new handover.

**Recall** uses the human's Google member to authorize a return from the multisig kiosk. It unequips
into that kiosk, then issues exclusive PurchaseCaps for the character and precisely its CURRENT
equipped items. The claim settles their policies and re-equips those items atomically in the human
kiosk. The original delegation loadout is not used; unrelated inventory stays put.
The SDK verifies the offer transaction’s ItemUnequipped events and unchanged newly created
capabilities before review and again before signing. Missing or ambiguous history, ownership or
gear blocks the claim. A failed claim leaves all transfers unexecuted; reconcile uncertain digests
before trying again. Cancelling releases the character and item listings in the source kiosk,
leaving the gear unequipped there. This uses existing contracts and needs no new Move module.
The human then checks incoming returns and claims into their own personal kiosk. Both signatures
come from the human; the agent is not asked. The first transaction needs multisig gas; the claim
needs human-wallet gas. Pending initial handovers can be cancelled through Recall; pending returns
can be cancelled from the incoming list.

This follows existing custody rules: a fighting character must first return to kiosk custody;
a capability already transferred to a third party is controlled by that holder. Recall does not
revoke the agent's 1-of-2 authority over assets remaining in the multisig.

## Selective inventory recovery

The human opens Recall, then refreshes Agent inventory. The read covers every personal kiosk,
address-owned object page, kiosk character's current equipment, liquid SUI/KARES, kiosk sale
proceeds and KARES staking positions. Unknown Move types are visible read only. Fighting
characters remain subject to existing settlement and are outside the kiosk inventory until returned.

Select exact items (whole stacks) and token amounts. Available, equipped, public-listed and
exclusive-offer items have distinct controls. Current equipment is checked before unequipping;
public listings can be cancelled first. Directly address-owned game items are deposited into a
personal kiosk before exclusive offer. The human then selects incoming item caps to claim or
cancel. Gear tied to a pending character return is excluded from independent item claims.
Kiosk proceeds and staked KARES are withdrawn to the multisig first; refresh before selecting
an external recovery amount. Everything reuses existing kiosk, marketplace and staking primitives.

SUI review retains an editable reserve, initially the existing SDK gas budget (0.05 SUI).
Variable-sized recovery batches use the existing fee estimator. Fresh balance must cover the
chosen SUI amount, the full prepared gas budget and the explicit reserve. Coin transfers never
implicitly drain all funds. Missing KARES deployment pins disable that currency without hiding
items or SUI; staking additionally requires its ordinary currency/pool/reward pins. Check live state again before signing; an uncertain digest must be
reconciled rather than retried. These checks do not suspend the trusted agent's concurrent actions.

## Verification boundary

Gas failures open the existing funding flow for the actual payer: multisig for the Recall offer,
human for the claim. No funds are sent automatically.

Local tests cover identity binding, signed-mode tampering, both custody builders, equipment reads,
Google-member envelope wiring with an explicit verification stub, public identity recovery and
failed/uncertain submissions. Actual Google proof verification, host-key persistence and the full
live handover/Recall round trip remain for the human's manual test after deployment. The optional
`agent_kit.ts` observer is a diagnostic example, not a required runtime or autonomous player.
