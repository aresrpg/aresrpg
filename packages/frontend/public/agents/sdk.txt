# SDK reference and offline planning

First complete [Connect Your Agent](https://aresrpg.world/agents/client.txt), the single official
supported bot onboarding flow. This reference describes the SDK actions used by the hosted executor after onboarding.
Assistants call the currently exposed subset through MCP `tools/list`, not arbitrary SDK methods; they never receive a signing adapter or private key. It does not offer separate manual-wallet
onboarding. The optional observation example does not limit the SDK's action capabilities.

## Offline planning

For developers inspecting a matching source checkout (not required for MCP onboarding):

```sh
bun packages/sdk/examples/agent_plan.ts recall_potion 1
bun packages/sdk/examples/agent_plan.ts recall_potion 10 5
```

The planner requires no wallet, network request, or payment. Its arguments are output item type, current job level, and attempted quantity. It prints eligibility, required job/level, initial displayed success chance, initial XP per attempt, ingredients, and authored sources. At job level one it correctly marks recall potions ineligible. At level ten it expands the materials for five attempts, not five guaranteed outputs.

The displayed percentage uses the existing UI helper, which floors fractional percentages. Batch odds and XP can change as attempts level the job. Inspect the exact aggregate craft owner for financial modeling. Authored source rows do not establish live availability: a listed mob may belong to a dungeon or protector encounter, and a resource row may have no spawning biomes/cities.

## Private actor and browser SDK integration

In the browser, use the existing authenticated `AuthSession` from `@aresrpg/sdk/auth`. It already exposes `character`, `fight`, `dungeon`, `marketplace`, `party`, `mastery`, trade builders, balance reads, personal-message signing, and transaction observation. Do not read a private wallet key out of the browser.

Inside the hosted execution service only, the managed signing adapter composes the existing SDK
action builders. It is not returned by OAuth or MCP. Service configuration supplies matching
network/pins, a compatible gRPC endpoint and durable transaction recovery storage.

This fragment assumes `managed_signer`, `network`, `pins`, `rpc_url` and `transaction_journal` have
been configured internally by the execution service, never by the assistant:

```ts
import { SDK } from './packages/sdk/src/client.ts'
import { create_agent_actions } from './packages/sdk/examples/agent_actions.ts'

const address = managed_signer.address
const sdk = SDK({ address, sign_transaction: managed_signer.sign_transaction,
  network, pins, rpc_url, transaction_journal })
const actions = create_agent_actions(sdk, address)
const balance_mist = await sdk.read_sui_balance()
```

Paths above are for a script at the repository root. Inside a workspace, use declared package exports where available. Some domain builders are reached through `AuthSession` or source-relative imports; inspect `packages/sdk/package.json` before inventing subpath imports such as `@aresrpg/sdk/fight`.

`create_agent_actions` demonstrates construction of existing domain builders with a personal-kiosk loader. It adds no budget enforcement, wallet permission UI, autonomous loop, or general read client. Its methods perform real transactions. Merely constructing it or calling the offline preview does not.

The hosted backend actor supplies the awaited `TransactionJournal` seam exported by `@aresrpg/sdk/transaction-execution` through `SDK({ transaction_journal })`. Its durable journal encrypts exact prepared/signed transaction envelopes and retains receipts across actor failures. Signing and submission must await the journal transitions; storage failures stop execution. Recovery belongs to the same SDK executor under current authorization and a fenced wallet lane, not an assistant retry loop. See the [journal implementation](https://raw.githubusercontent.com/aresrpg/aresrpg/edge/packages/bot/src/transaction_journal.ts) and [operator README](https://raw.githubusercontent.com/aresrpg/aresrpg/edge/packages/bot/README.md).

Browser `transaction_storage` is a different, synchronous digest-only recovery seam (`getItem`, `setItem`, `removeItem`); it does not retain signed bytes and is not the hosted actor journal. Keep signatures and exact envelopes out of chat, logs and activity ledgers. Only the trusted backend can decrypt its envelope journal. External assistants never receive keys or signing adapters.

## Chain-native read adapter reference

Use a separate Sui GraphQL reader and keep the SDK writer on gRPC. This bounded object-read fragment assumes `graphql_url`, `network`, and exact `object_ids` have already been selected for the deployment:

```ts
import { SuiGraphQLClient } from '@mysten/sui/graphql'

const reader = new SuiGraphQLClient({ url: graphql_url, network })
const { objects } = await reader.core.getObjects({
  objectIds: object_ids,
  include: { json: true },
})
```

This returns chain objects, not SDK-ready gameplay rows. Validate each result's identity/type/version and missing/error state before decoding it. Read the necessary dynamic fields and related custody objects, paginate discovery, and retain certified versions. Inspect the installed client's `core` API and current provider schema instead of inventing GraphQL field names. The reader is an external script integration; the game frontend continues to use its existing indexed read owners.

Follow [the read-model checklist](https://aresrpg.world/agents/protocol.txt) before passing inputs to an action. Source content comes from the matching published deployment, with `seed/content` as its authored reference. Live custody, consumed zone slots, listings, checkpoints and fights come from fresh chain reads. The SDK resolves transaction references; it does not build your inventory, zone population or hydrated combat model.

For combat, decode the complete current Fight and player-source state, then attach matching authored spells and normalize integers through the existing fight/content owners. Neither a raw GraphQL object nor `packet/fight_state` is already a `HydratedFightCheckpoint`. Do not cast JSON to that type just to satisfy TypeScript. The existing zone population twin is likewise needed to derive targets from seed/generation and consumption. These docs do not provide a complete standalone decoder/discovery client.

Keep GraphQL reads bounded, account for provider quotas and checkpoint visibility, and wait until post-write reads include the certified versions. Do not pass the reader as the SDK write transport: writes require `rpc_url`/gRPC for full receipts.

## Alternative: consume AresRPG's indexed inputs

Use the [game-server protocol](https://aresrpg.world/agents/indexing.txt) with the paired multisig
for prepared account/world/fight rows and online presence. Direct GraphQL reads remain useful SDK
inputs after onboarding; selecting a read source is not a separate account-setup path. The server
does not relay transactions: the SDK submits them through gRPC.

Both integrations use the same action builders below. The host supplies validated current inputs and policy; switching the read source does not change gas costs, signer authority or transaction recovery.

## Existing action map

The names below are methods on the authenticated session or the example's `actions` object. Read their TypeScript signatures for exact input types.

| Intent | Existing method |
| --- | --- |
| Create character | `create_character(input, first_world)` |
| Equip or unequip a reviewed set | `character.equip` |
| Allocate capital / raise a spell | `character.raise_stats` / `character.raise_spell` |
| Change world / discover a zone | `character.join_world` / `character.search_zone` |
| Harvest / resolve protector | `character.gather` / `character.resolve_ambush` |
| Craft / consume / feed | `character.craft` / `character.use_consumable` / `character.feed_pet` |
| Start/join/place/ready fight | `fight.engage` / `fight.join` / `fight.place` / `fight.ready` |
| Submit a complete turn | `fight.commit_turn` |
| Timeout / forfeit / settle | `fight.crank` / `fight.forfeit` / `fight.settle` |
| Enter dungeon / start or join room | `dungeon.enter` / `dungeon.start_fight` / `dungeon.join_fight` |
| Progress dungeon / leave | `dungeon.settle` / `dungeon.give_up_fight` / `dungeon.abandon` |
| Buy/list/delist/collect | `marketplace.buy` / `marketplace.list` / `marketplace.delist` / `marketplace.collect` |
| Start Mastery / redeem offer | `mastery.start` / `mastery.redeem` |
| Invite/accept party | `party.invite` / `party.accept` |
| Operate a current trade | `trade(fresh_trade_row)` then its typed methods |

The browser session also exposes Kolizeum, friends, giftcards, finance, and other specialized actions. Consult its exact surface before using them. The example factory intentionally covers the core playbook; it does not impersonate every `AuthSession` facility.

## Example: one approved gather

Given a fresh owned character row, a current live resource pack, and the matching published resource row:

```ts
const result = await actions.character.gather({
  character_id: character.id,
  custody: { kiosk: character.kiosk, kiosk_cap: character.kiosk_cap },
  world: character.world,
  zone_x,
  zone_z,
  pack_index: pack.index,
  item_type: resource.item_type,
  rare_item_type: resource.rare_item_type || null,
  existing: null,
  existing_rare: null,
})
```

This is an integration fragment, not a complete loop: prove current world, tool/job eligibility, generation, travel, readiness, and spending before calling it. `existing: null` permits a new stack instead of guessing a merge target. Prefer a verified available compatible stack when practical. After success, log the digest and await the new checkpoint/consumption. If `ambushed` is true, stop harvesting and resolve the retained protector policy.

## Example: calculate when to act

`earliest_travel_ms(character, { x, z })` from `agent_plan.ts` finds the first integer millisecond accepted by the protocol's existing travel predicate. It returns null for missing/mismatched checkpoint state, out-of-world coordinates, active dungeon runs, or a pending protector. It is a travel calculation, not complete authorization: also require free custody, fresh state from the chosen read path, live target, and budget.

Schedule an inspection around that result. Execute only after a fresh observed chain timestamp satisfies `travel_proof_ready` for the latest character and target. A checkpoint change invalidates the previous deadline. Keep the original chain sample age; receiving cached clock data does not make it new.

## Example: plan and commit a combat turn

Use a fully hydrated, current authoritative checkpoint. Derive the active seat from its queue and verify ownership. Use target/path helpers to construct a short array of SDK actions, then:

```ts
import { preview_turn } from './packages/sdk/examples/agent_actions.ts'

const predicted = preview_turn(checkpoint, planned_actions)
```

The helper clones the checkpoint, maps SDK actions to simulator commands, and rejects illegal actions or missing witnesses. It previews the current ordered actions only; it does not generate future randomness, finish the turn, or spend anything. Compare independent candidates by survival, useful damage/control, and end position. Inspect `predicted.contract` to score outcomes.

After the player policy, fresh turn identity, minimum deadline, and spending checks pass:

```ts
const result = await actions.fight.commit_turn({
  fight: checkpoint.contract.id,
  actions: planned_actions,
})
```

The SDK appends the correct terminal boundary. Observe `result.turn_witnesses` and fresh chain state (or the chosen indexed stream). Never reuse the same action array against a different turn or submit it again because the receipt arrived before the server update.

## Example: bounded crafting

Run the planner first. Read the published recipe and arrange `input_item_ids` in its actual ingredient order. Select available holdings in the crafter's custody and provide explicit merges for fragments. Then call `character.craft` with `character_id`, `custody`, `output_type`, `input_item_ids`, `existing`, `attempts`, and optional `merges`.

Use `existing: null` for a unique output. For stackables, a verified compatible destination may be supplied. Spend only ingredients for the approved attempted quantity. Record actual successes and job XP, then recalculate the remaining target. Do not interpret a zero-success receipt as a network failure.

## Spending observation and stop behavior

Subscribe to `sdk.on_transaction` before the first paid operation. Its callback receives `{ digest, outcome, gas_mist? }`; persist those certified facts by digest. The host must stop further writes if ledger persistence fails. Treat quoted payment and actual balance effects separately from gas.

Do not use `Promise.all` for dependent wallet actions. Do not add catch-and-retry around a domain method. The SDK already handles its narrow proven-unsigned preparation cases; unknown or executed outcomes must enter recovery. A loop should select a new intent only after its previous intent is reconciled.

When extending beyond the examples, first exercise pure planning against fixtures. Typecheck with the repository packages. Test an explicitly authorized testnet account before mainnet execution. A successful typecheck proves API compatibility, not combat success, profitability, or permission to spend.
