# Tactical combat

Combat is a deterministic state machine with committed randomness. Move enforces it; `@aresrpg/fight` is the TypeScript twin. Use the twin to inspect legal actions and simulate drafts. Never replace it with an approximate damage calculator for transaction planning.

## Discover spells and spend spell points through MCP

Use `bot_observe` with `{"spells":[]}` (the default full view) before authoring tactics. Read
`planning_context.spells.catalog`: every row has `name`, `classe`, and `unlock_level` from the
same authored spell corpus used by the executor. `name` is the exact, case-sensitive spell ID
for cast steps and upgrades; there is no separate numeric ID to look up. No source checkout is needed.

Then call `bot_observe` with `{"spells":["Tricky Trap","Mass Trap"]}`. The response's
`planning_context.spells.definitions` contains all authored ranks in `levels` (rank 1 is index 0),
including AP cost, minimum/maximum and modifiable range, line of sight, line launch, per-turn/per-target cast limits, cooldown, critical rate, and
normal/critical effects. `free_cell` is retained wire metadata, not a universal empty-target rule;
occupied-cell legality follows the effect kind and fight twin.
The accompanying `effect_kinds`, `area_shapes`, `target_filters`, and `stat_channels` maps decode
the numeric effect fields directly from the Move-derived fight vocabulary. A zero cast limit means
no limit beyond other rules such as AP; `crit_1_in` is a one-in-X rate, not a percentage.

Each definition also has `characters` keyed by `character_id`. Match the intended character from
the observation's owned roster: `learned_rank` is null for a wrong class, insufficient character
level, or unavailable rank. A missing investment in the character's spell book means rank 1 once
unlocked, not an unlearned spell. Catalog membership does not grant entitlement, and a learned spell
may still be illegal this turn because of AP, range, targets, cooldown or fight state. Use
`bot_validate_combat_profile` for the selected character before saving tactics; live fight-seat
`planning_context.fights` and the fight twin remain the owners of current casting legality.

`available_spell_points` is the observed balance. `upgrade` is a one-rank quote `{cost,next_rank}`,
or null when no upgrade exists (locked/wrong-class/invalid rank or already at the authored cap).
Rank n to n+1 costs n points. A quote is not permission: the character must still be owned by the
agent, in kiosk custody without an active fight, and have at least that many available spell points.

To perform an explicitly authorized upgrade, call `bot_raise_spell` with:

```json
{
  "idempotency_key": "<unique upgrade intent>",
  "decision_revision": 0,
  "observation_revision": 0,
  "action": {"character_id":"<owned character ID>","spell":"Tricky Trap"}
}
```

Replace both revision placeholders with the latest full observation's revisions. This requires
`bot:play` and submits one ordinary SDK transaction, raising exactly one rank. It also works as
a behavior `call` action with `kind: "raise_spell"` and that same action object as `payload`.
Read `bot_status` with the returned command ID and observe the new rank and spent points before
planning another upgrade. Preserve the same idempotency key for the same intent. An executed
failure or uncertain transaction is never automatically retried; use the existing status/recovery flow.
Spell-point spending is separate from saving combat preferences or allocating characteristic points.

Omit `spells` for ordinary live observations without the static catalog. A changes-only observation
omits planning context; request full for discovery. If observation returns pending, repeat the read;
if planning context is unavailable/needs_resync, obtain a fresh observation before planning.

## Tell your assistant how to fight

Describe the character's role and the order that matters: "Play this character strength-based. Place traps first, then retreat." You can also ask "Use this spell combination before attacking", "Focus the lowest-health enemy", or "If nothing is useful, stop and ask me." The assistant should explain the saved tactics in ordinary language and name any spell or behavior it cannot support. A strength preference does not allocate points or equip items; those are separate actions.

Hosted assistants can remember a profile with `bot_save_combat_profile`, after reading its revision with `bot_combat_profile` and checking it with `bot_validate_combat_profile`. To execute it, author a behavior tree with a `combat` action containing explicit profile snapshots for every owned participant, validate it with `bot_validate_behavior`, then call `bot_start_behavior` with fresh observation/decision revisions. The leaf binds one existing ordinary PvE fight, keeps the current legal placements, readies participants, plays their turns and settles through normal game actions. Its durable activation survives waiting and restart. The assistant can compose an explicit `engage` action and reactive conditions to choose subsequent fights. Dungeon, tournament, wagered and other unsupported modes remain unavailable through this hosted leaf. The bot executes accepted trees while the assistant is offline; it never contacts an AI provider. Planning and replanning happen only when an external assistant calls MCP.

A profile uses this finite JSON vocabulary (example for a Yajin who can use Tricky Trap):

```json
{
  "version": "1",
  "intent": "Strength-based; place traps then retreat.",
  "combos": [
    {"name": "traps", "steps": [{"type": "cast", "spell": "Tricky Trap", "target": "trap_near_enemy"}]},
    {"name": "escape", "steps": [{"type": "move", "direction": "retreat"}]}
  ],
  "rules": [
    {"when": {"type": "always"}, "combo": "traps"},
    {"when": {"type": "always"}, "combo": "escape"}
  ],
  "fallback": "end_turn"
}
```

Each rule runs once per turn against the updated simulation. An unavailable combo step stops that combo and keeps its legal prefix; later rules continue, so retreat can still happen when a trap is unavailable. Conditions also support `{"type":"hp_below","percent":40}` and `{"type":"enemy_within","cells":3}`. Cast targets are `self`, `nearest_enemy`, `lowest_hp_enemy`, `highest_damage_enemy`, `trap_near_enemy`, or `most_allies`; weapon strikes support the three enemy selectors. Movement is `approach` or `retreat`. Names refer to actual game spells, with current class, unlock level and invested spell level checked. A trap's empty-cell choice is a simple deterministic heuristic, not a prediction that enemies must walk onto it. Retreat prefers survival and remaining HP before greater distance from the nearest enemy; walls, tackle and traps can prevent escape.

For wall-aware pushing in an autonomous sequence, use `{"type":"cast","spell":"Tricky Blow","target":"highest_damage_enemy"}`. This selector simulates each legal enemy aim from the current position and chooses the greatest total enemy HP loss, including wall, body and board-edge collision damage. Overkill counts only HP actually lost. Ties keep nearest-enemy order, then fighter index. Subsequent steps see the resulting displaced fighters and spent AP. By default it does not move. Add `"position":"best_damage"` to a cast or strike step to compare its current aim with move-then-attack sequences over canonical reachable cells. For example: `{"type":"cast","spell":"Tricky Blow","target":"highest_damage_enemy","position":"best_damage"}`. The target selector still applies at each position; use `highest_damage_enemy` to compare every legal enemy aim rather than only the nearest or lowest-HP enemy. Each route and attack use the real simulator, including tackle, traps, AP/MP, line of sight and occupancy. It chooses total enemy HP loss, then acting-fighter HP, remaining MP and fewer actions. A route that kills the actor or leaves no legal attack is rejected. Search uses one canonical shortest path per reachable endpoint, not every possible route, and does not optimize future turns or penalize allied damage. Existing `approach` and `retreat` steps remain separate heuristics.

For ally support, use `{"type":"cast","spell":"Pack Totem","target":"most_allies"}`. The selector simulates every legal cast cell from the current position. It counts distinct living, non-forfeited same-team recipients, including the caster. Immediate support counts actual net HP/AP/MP gains or increased positive stat-add totals. New glyphs count potential positive-add payload coverage at current occupied cells, using the canonical turn-start target geometry and filters. Pack Totem therefore prefers covering allies rather than aiming at the nearest enemy. Placement does not apply its buff immediately: it triggers when a fighter starts a turn inside the glyph. Future occupancy, survival, expiration, rolls and healing need can change the result; this coverage is not guaranteed future benefit. Existing glyphs and buffs do not count as new support. Zero recipients skips the step; equal counts retain canonical legal-cell order. This is a coverage objective, not a magnitude, shield, dispel, trap, damage-risk or general utility score. It performs no movement and cannot combine with `position: "best_damage"`.

Use `fallback: "awaiting_ai"` to request a new external decision when the entire turn has no legal configured action; `end_turn` passes instead. Check `bot_behavior_status` for the exact blocker and last command. `awaiting_ai` does not call an AI service. After admitted work reconciles, the assistant may explicitly `bot_replace_behavior` with the current run revision and fresh lane revisions. Saving a profile alone never changes the active tree's embedded tactics. Failed or uncertain transactions require review; a selector cannot hide them by submitting another branch. `bot_stop_behavior` fences new admissions without forfeiting; signed work can be cancelled only before submission wins, and already submitting work keeps exact receipt recovery. Owner Disconnect/Recall remains the asset-return operation. Wallet funding remains the spending limit.

Behavior trees have ordered sequences, priority selectors, reactive conditions, explicit loops and action leaves. Reconciled actions remain completed within their traversal while conditions are reevaluated. Switching branches clears abandoned memory; unknown facts wait instead of becoming false. A successful root repeats on the next scheduler tick, so add an explicit `complete` leaf to stop at the intended observed objective. No default duration or action-count limit is imposed. Other authored branches can gather, craft, discover resources, equip owned items or buy/sell observed market lots through the same wallet lane. Market selection follows all server pages but sees only the three cheapest offers per group, across a live non-atomic sweep. A buy maximum covers actual ask plus royalty, excluding gas. Existing legacy combat/profession records remain recoverable; new automation uses behavior trees.

## Before engagement

Inspect the actual mob group: identities, scaled levels, HP, resistances, AP/MP, and spell kits. Archimobs are separate stronger identities, not cosmetic names. Check your current HP, equipped weapon, allocated stats, raised spells, consumables for later recovery, and available gas for the whole fight including settlement.

Choose encounters by expected success, turns, XP, loot relevance, and recovery cost. Do not equate “I meet the world entry level” with “I can beat every group here.” Start with a small safe sample and measure actual outcomes before increasing difficulty.

For groups, agree on access, participants, roles, and who starts. Each participant must join legally before readiness closes placement. A player controls only their own seats. Six lifetime admissions per side limit the fight; rotating forfeited characters does not create unlimited reinforcements.

## Fight lifecycle

1. Engage the exact live group or join an eligible fight. Dungeon fights use the dungeon builder.
2. Read the authoritative fight checkpoint and identify each owned seat.
3. Place on allowed, unoccupied start cells. Cover useful lanes and avoid immediate enemy area damage.
4. Ready after the intended team is seated. Final readiness can start combat atomically.
5. For each owned active turn, simulate a legal ordered action sequence, then commit it once.
6. Observe the certified boundary and reconcile the next checkpoint before planning again.
7. At the terminal state, settle every owned seat with its correct loot plan and custody.
8. Confirm returned characters, HP, XP, loot, and any pending recovery before continuing.

Force start becomes eligible after the placement deadline, currently 60 seconds. End Turn has a minimum elapsed time, currently 3 seconds from the current turn start. Timeout crank for a living active fighter requires 45 seconds. Use `CONTRACT_CONSTANTS` and fresh chain time, not local wall time. Do not assume a dead active fighter uses the living timeout path; the normal SDK terminal door handles the post-action boundary.

## Read the board and active state

Chain-native agents must decode and hydrate the current Fight plus its source data; the indexed projection prepares wire rows but still needs hydration. See [the SDK cookbook](https://aresrpg.world/agents/sdk.txt). Do not assume a generic GraphQL object read is a ready-to-simulate checkpoint.

Use the checkpoint's cells, closed mask, queue, active pointer, living fighters, current AP/MP, effects, cast ledger, cooldowns, and source spell data. Cell IDs are fight-grid identifiers, not overworld coordinates. Keep integers as bigint in the fight runtime.

The normal base pools are 6 AP and 3 MP, but gear and effects change them. The current state is the usable budget. A unit with enough MP may still suffer tackle losses when leaving an adjacent enemy. `fight_path_to` and `reachable_fight_cells` find geometric routes; applying the movement command determines actual tackle, trap, and movement effects.

For every spell, inspect:

- Learned level, AP cost, minimum/maximum range, and whether range is modifiable.
- Line launch, line of sight, and effect-specific target occupancy through the fight twin.
- Casts per turn, casts per target, and cooldown.
- Area shape, size, target filters, normal effects, and critical effects.
- Push/pull/swap, healing, shields, buffs, removals, traps, glyphs, summons, or other state changes.

Use `spell_target_cells`, `weapon_target_cells`, `preview_spell_cast`, and `preview_weapon_strike` for legal targeting and explanation. Use `project_spell_turn` and `project_weapon_turn` or a cloned `create_fight` runtime for actual sequential outcomes. A preview is neither submission nor authority.

## Hosted MCP cast and collision analysis

Call `bot_observe` with `fight_plan: { character_id, fight, fighter_idx, checkpoint_id, actions: [] }`, using IDs from a fresh full observation. The optional full-view result lists the board cells and legal next targets for each learned spell and the weapon. An empty target list means no legal cast now, not an unlearned spell.

To inspect a candidate, pass the same object with ordered `move`, `cast`, or `strike` actions in the `bot_fight_turn` vocabulary. The remote fight twin replays that prefix and returns predicted events and resulting fighters, then recalculates next casts. Compare separate requests to explore movement-before-cast and alternative aims. `fighter_moved` records each actual step; `push_collided` reports the target, remaining blocked cells and collision damage. A failed action reports its index and engine reason; remaining actions are not run and no continuation targets are offered. Returned events and fighters then describe only the successful prefix.

For example, inspect Tricky Blow from the current square, then from a reachable adjacent approach square. Push direction derives from the caster and target positions, so changing the caster's side changes which wall the target approaches. Closed cells, living bodies and board edges can stop a push. Use the returned collision events rather than inferring damage from distance or spell text.

This is a read-only current-turn prediction based on the observed checkpoint and the twin's authored sources. It performs no transaction simulation/signing and confirms no execution; it supplies no future turn entropy. Reobserve before any submission. For autonomous execution, put `highest_damage_enemy` in the combat profile embedded in your behavior tree; the bot evaluates it each turn without contacting an AI. Explicit action previews remain useful for comparing a particular path or aim, but do not alter an accepted behavior.

## Damage, defense, and effects

Elemental damage uses the matching characteristic and raw damage, then the target's resistance and active effect rules. Integer rounding matters. Multi-line weapons can behave differently from one large hit. Inspect critical effects separately; a critical does not always mean multiplying normal damage by a fixed number.

Resistance is element-specific and capped by the combat rules; weaknesses can increase damage. Shields/reductions, redirection, reflection, spell return, healing conversion, and immunity can change the target or result. Calculate through the twin instead of estimating from the tooltip headline. Healing scales differently from damage. Player drains heal from actual HP lost by the intended target; redirected or converted damage can yield no drain heal.

AP/MP removal and tackle are contests, not guaranteed effects from their displayed magnitude. Evaluate both the expected benefit and the consequence of failing. Use the current state after each command; a buff, debuff, push, death, or displacement can invalidate the next action.

Timed fighter effects count down at the affected fighter's turn end. A zero row remains active until that fighter's next start, where expiration precedes AP/MP modifiers, poison/regeneration, and glyph refresh. Glyph lifetimes and spell cooldowns have their own clocks. Do not implement one generic “decrement everything each round” rule.

## Plan a turn

First prevent a likely loss. Then remove enemy actions efficiently. A useful priority order is:

1. Avoid lethal incoming damage to a critical teammate or yourself.
2. Kill or disable a dangerous enemy before its next action.
3. Preserve a safe end position and reachable allied support.
4. Exploit elemental weaknesses, efficient areas, and AP combinations.
5. Improve next-turn positioning without wasting current damage or healing.

Compare attack-before-move and move-before-attack sequences. Moving first can leave range, trigger tackle, or consume the MP needed to escape. Focus fire often prevents more damage than spreading it, but a control spell or area finish can be better. Avoid damaging allies through area effects. Leave lanes for teammates and respect their declared plans.

Bound the search. Enumerate legal targets for a few useful spells and weapons, plus safe movement destinations. Simulate candidate prefixes on independent clones. Rank survival first, then enemy actions prevented, useful damage/healing, control, and final position. Keep a short beam of alternatives until AP or a small search budget is exhausted. Do not block the real turn deadline chasing an exhaustive optimum.

Evaluate uncertain future enemy turns with multiple scenarios if useful. Label them forecasts. The current committed turn stream can be simulated; future entropy is not yours to invent. `mode: 'local'` is for offline scenarios, not proof of future on-chain outcomes. In `mode: 'remote'`, a boundary may await certified seed witnesses; wait or replace from a freshly decoded chain checkpoint (or the indexed checkpoint) rather than fabricating a seed.

## Commit exactly the reviewed draft

`fight.commit_turn({ fight, actions })` accepts ordered SDK actions:

- `{ type: 'move', path: bigint[] }`
- `{ type: 'cast', fighter_idx: bigint, spell: string, target_cell: bigint }`
- `{ type: 'strike', fighter_idx: bigint, target_cell: bigint }`

This is a different vocabulary from the simulator's `move_to`, `cast_spell`, and `weapon_strike` commands. The [action example](https://raw.githubusercontent.com/aresrpg/aresrpg/edge/packages/sdk/examples/agent_actions.ts) maps them explicitly.

The builder appends the terminal End Turn door. Do not send one transaction per spell or append a second boundary yourself. Do not append arbitrary calls after a Random-consuming terminal door. If a final strike kills the last enemy, use the same builder; Move decides whether to advance or seal the fight.

Recheck fight ID, owned active seat, round, turn pointer, turn-start timestamp, and checkpoint freshness immediately before signing. Discard a stale draft. Courtesy websocket actions are only previews; a received draft never authorizes the agent to spend SUI or commit another player's turn.

After a rejected unsigned draft, read current truth and replan. After an executed failure or uncertain submission, stop and inspect the digest. Do not “fix” a path and automatically submit again while the first outcome is unknown.

## Rewards, group scaling, and settlement

Group XP comes from the defeated mob pool, a party coefficient, level matching, each player's level share, and Wisdom. Personal damage is not an XP ownership meter. Very low-level members do not necessarily increase the party coefficient. Use `xp_award_of` for the actual terminal checkpoint instead of promising simple multiplied XP.

Defeated mobs produce shared loot rolls; winning seats share successful drops. Adding players does not duplicate each mob's loot table. Plan with group allocation and prospective costs in mind. A low-damage support can still be worth bringing because it changes the chance or speed of victory.

Use terminal source loot tables and the existing result planner as the model for settlement inputs. A winning seat needs the complete eligible loot-template set, not only the item you hoped to get. Group settlements by destination custody. Use `dungeon.settle` for dungeon progression and Mastery eligibility, and request boss reward preparation when the terminal fight is eligible. Do not default every encounter to a boss.

Characters remain unavailable while held by a fight even if the UI animation has ended. Settlement returns custody and writes persistent HP/XP. For chain-native recovery, inspect the retained Fight identity, owned seats, settlement flags and current custody through chain reads and certified receipts. The indexed projection prepares `packet/fight_resolutions` and `packet/closable_fights` for remaining settlement/cleanup. Neither packet is a prerequisite for direct SDK settlement. Resolve only the remaining work. Fight discovery expiring does not erase your seat or its owed settlement.

Losing or forfeiting costs time, gas, and health. Explain that tradeoff before an unapproved retreat. When retreat was authorized, use the correct normal/dungeon forfeit path and verify the return. Report losses honestly; do not call a forfeit a win because the resource harvest survived.
